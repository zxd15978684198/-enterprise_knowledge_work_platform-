# ADR-0012：真实后端接入范围（MinIO / Celery / 模型 provider）

- 日期：2026-10-29
- 状态：**提议**（范围豁免属产品裁决；工程侧给出接入顺序与验证口径）
- 依据：`Phase0_Full_Gate_Review.md` §3（PoC-02/03/06/09 判定）、§6.1 ADR-NEW-6、§6.3 DG-2/DG-3/DG-4；`05_Phase0_Acceptance.md:70`、`:80`

## 背景

T32 复核发现 P0 的四类真实后端全部没有跑过真实形态：PoC-02 使用真实 Redis 与真实 Celery 配置但未起真实 worker 跑通 60s deadline；PoC-03 只用本地/InMemory 对象存储，未验证真实 S3/MinIO 与删除传播；PoC-06 的 provider 是替身，`stream()` 未实现；PoC-09 因缺 ANN 只能做两路对照。结果不是「功能没做」，而是**「功能做了但后端是替身」**——这类结论极易被误读为已通过，因此必须有一条编号决策明确「P0 到底豁免不豁免真实后端」。

`05:70` 规定单活降级只能形成限域建议；`05:80` 要求高风险项「已验证或经正式范围变更排除且明确禁用」。两条都指向同一个要求：豁免真实后端必须写成**范围变更**，而不是让 PoC 判定默默停在 PARTIAL。

## 决策提议

1. **P0 明确豁免真实后端**，其出口形态只能是「**受限范围准入**」，不得表述为 G-FULL 通过；豁免清单与 DG-2/DG-3/DG-4 一一对应。
2. **P1 首批接入顺序固定**（前一项不通过，后一项不开工）：
   1. MinIO / S3 兼容对象存储 → 重跑 T12（staging/引用模型）与 T13（原子发布、删除传播）；
   2. Celery 真实 worker → 按原样重跑 T08 的 60s deadline、重试、死信；
   3. 模型 provider（含 `stream()`）→ 重跑 PoC-06 与 T19 的 Gateway/Registry 用例；
   4. pgvector ANN → 与 ADR-0010 的重采 + T25 补跑合并执行。
3. **每接入一项必须重跑对应 PoC 并更新判定**：旧判定不得直接改文字，采用「追加一行：因 ADR-0012 第 N 项接入，重跑于 <日期>，结论 <X>」的形式。
4. **对外表述约束**：发布文档与 README 中不得出现「已验证真实 S3 / 已验证真实模型」等表述，除非对应 PoC 有真实后端证据。

## 替代方案

1. 用 MinIO 的 `file` 后端冒充 S3：不算真实后端（无网络、无预签名、无删除传播语义），拒绝计入 PoC-03。
2. 用 Celery `eager` 模式冒充 worker：不经过 broker 与并发语义，拒绝计入 PoC-02。
3. 用本地 llama.cpp/本地小模型代替厂商 provider：是「真实模型」但不是「真实 provider」，可作为 PoC-06 的过渡证据，需在判定中写明区别，不得混为一谈。

## 后果与验证条件

后果：P0 交付物只能声明「检索/事件/审批在替身后端上成立」，对象存储与模型能力不可对外声称；P1 排期必须把四项接入作为独立波次，且每项都带重跑成本。验证条件：(1) 受限准入文档列出豁免清单且与 DG 编号一致；(2) 每项接入后对应 PoC 的判定更新可追溯；(3) 全仓 SBOM 在 MinIO/模型权重接入后必须补齐（当前尚不存在）；(4) 若产品决定 P0 就要求真实后端，则本 ADR 被否决，G-FULL 解锁路径改为「先接入后评审」。
