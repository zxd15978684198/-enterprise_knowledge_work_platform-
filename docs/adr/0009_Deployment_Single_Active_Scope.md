# ADR-0009：P0/P1 部署范围与单活边界（补充 ADR-0006）

- 日期：2026-10-29
- 状态：**提议**（依赖并限域 [ADR-0006](0006_Single_Active_Checkpoint_Runner.md)，不改其正文）
- 依据：`poc01-owner.md:179`、`:186`；`poc01_owner_process_level.json`（T05R）；`P0_Core_Gate_Review.md` §3.3；`Phase0_Full_Gate_Review.md` §6.1 ADR-NEW-3、§6.3 DG-1

## 背景

ADR-0006 已就 **P0 单活 checkpoint runner** 给出决策提议：同一 run 同时最多一个写入进程，禁止自动接管。T32 在审阅时指出，这一结论目前只覆盖「checkpoint 写入」，尚未上升为**部署范围**层面的决策：P1 是否仍单活、多实例高可用如何立项、发布文档必须承载哪些残余风险，都没有成文。而 `05:70` 允许「单活降级只能形成明确限域建议」，`05:80` 要求高风险项「已验证或经正式范围变更排除且明确禁用」——两项都要求把单活写成有编号的、可被引用的范围决策，而不是散落在 PoC 结论里的一句话。

实测事实（不可弱化）：T05 观察到 backend 被终止后原生 `PostgresSaver` 的 put 仍成功；T05R 在进程级证据下确认「写进程存活、锁已释放、owner_epoch 推进到 2」之后原生 put 仍返回 `ACCEPTED`。结论是 advisory lock 只提供互斥，不提供写入授权。因此任何多实例共享同一 thread 的形态都存在双写风险。

## 决策提议

1. **P0 与 P1 首个版本均按单活 runner 部署**：同一 run 同时只有一个写入进程，由部署与调度保证唯一性；runner 崩溃后由人工或编排显式重启，新 runner 必须先阻塞取得 advisory lock、再 claim 新 owner epoch，**禁止自动接管**。
2. **多实例高可用不属 P0/P1 首发范围**，必须另立 ADR（新编号，不得复用本 ADR）。其前置条件是：把所有 checkpoint 写入收归「宿主持锁代理」，由代理在写入前校验 owner epoch（真正的 fencing），并给出故障模型与性能证据；在该 PoC 通过前，本 ADR 不批准任何多实例形态。
3. **发布文档必须承载残余风险模板**，至少三行，缺一不得发布：
   - 部署形态：单活、无 HA；故障恢复方式 = 停旧进程 + 起新进程，非自动接管；
   - 残余风险：原生 saver 路径在失锁后仍可能写入（双写窗口存在，靠运维纪律关闭）；
   - 可观测字段：`owner_epoch`、lease/attempt 账本、启动时的持锁日志。
4. 判定口径固定：checkpoint 相关任务判 `PASS（限域：单活）`，不得写无保留 PASS；发布说明中不得出现「高可用」「自动故障转移」等表述。

## 替代方案

1. 靠 advisory lock 做多实例互斥：已实测锁不约束原生写入路径，等于没有 fence，拒绝。
2. 自动接管（检测失锁后自愈）：会在旧进程仍写时产生双写，拒绝。
3. 宿主持锁代理统一写入：可恢复单写者语义，但需新增服务、故障模型、性能与运维证据，T05 未验证，留待独立 ADR + PoC。

## 后果与验证条件

后果：单 run 吞吐上限 = 单 runner；滚动升级必须先停旧起新，恢复时延可观测；`owner_epoch` 与 attempt 账本只承担审计与诊断，不承担跨进程写入授权。验证条件：(1) 部署清单中 runner 副本数恒为 1；(2) 每次发布文档含上述三行残余风险；(3) 若有人提议多实例，必须先开 ADR 并附代理 PoC，禁止直接改部署文档；(4) 进程级证据每次重跑都落盘并与本 ADR 口径一致。
